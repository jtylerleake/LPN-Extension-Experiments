---

## 1. What We Are Building and Why

This project extends the **Latent Program Network (LPN)** architecture (Macfarlane & Bonnet, NeurIPS 2025) with a module that makes the learned program representation *explicitly human-readable*. The original LPN learns an implicit continuous program vector $z$; our contribution is to add a structured readout head that decodes $z$ into an inspectable symbolic program during inference.

The core claim we are trying to demonstrate is: **LPN's latent vector $z$ already organizes itself around program structure. We can read that structure out.** The MLP head is an instrument for doing so — it is not changing what $z$ learns (much), it is rendering it legible.

The testbed is a simplified variant of the paper's Pattern-2D task.

---

## 2. Background: How LPN Works

LPN has three components that operate in sequence. It is critical to understand what each does and does *not* do, because our interpretability module is designed to make their implicit behavior explicit.

### 2.1 The Encoder

The encoder takes a set of input-output pairs $\{(x_i, y_i)\}_{i=1}^n$ and produces a latent vector $z_0$ that summarizes the "program" underlying those pairs.

Each pair $(x_i, y_i)$ is encoded **independently** by a small transformer, producing a per-pair mean and log-variance $(\mu_i, \sigma_i)$. These are then **mean-pooled** across all $n$ pairs to yield a single aggregate $(\mu, \sigma)$, from which $z_0$ is drawn (with reparameterization during training, or set to $\mu$ at test time).

**Why mean pooling is the key mechanism:** Mean pooling is what forces $z$ to encode only program-invariant information. Any property that is consistent across all pairs — the color tile pattern, for instance — will produce $\mu_i$ vectors pointing in the same direction, so the mean reinforces that signal. Any property that varies across pairs — the anchor pixel's position — will produce $\mu_i$ vectors pointing in different directions, so the mean cancels that signal out. The result is a $z$ that captures what is invariant across the specification, which is precisely the program.

The implication: **$z$ encodes the tile color pattern. It does not encode the anchor position.** The anchor position is variant and is handled separately by the decoder.

### 2.2 Latent Optimization

At **test time only**, LPN refines $z_0$ by performing gradient ascent in latent space. Starting from $z_0$, it iteratively updates:

$$z_k = z_{k-1} + \alpha \cdot \nabla_z \sum_i \log p_\theta(y_i \mid x_i, z)\bigg|_{z=z_{k-1}}$$

All encoder and decoder weights are **frozen** during this step. Only $z$ is updated. This is analogous to slow deliberate reasoning — the encoder gives a fast first estimate, and gradient ascent refines it. The result is $z^*$, the optimized latent.

**Training-time latent optimization** is optional and minimal (0–5 steps in the paper). The encoder is primarily trained by backpropagating through the reconstruction loss directly on $z_0$.

### 2.3 The Decoder

The decoder takes a pair $(x_i, z^*)$ and autoregressively generates the output $y_i$ pixel by pixel. It is a transformer that jointly attends to the flattened input grid $x_i$ (with its spatial positions encoded) and the latent $z^*$ (prepended as a special token).

**Critically: the decoder is a black box.** It learns through training to implicitly (1) find the anchor pixel in $x_i$ via attention, (2) read the tile color pattern from $z^*$, and (3) compose them into the correct output. None of these steps are hardcoded or explicitly supervised — the decoder learns them end-to-end from the reconstruction loss on $y$.

This is what we are making explicit.

### 2.4 Training Objective

The training loss is:

$$\mathcal{L} = \mathcal{L}_\text{rec} + \beta \cdot \mathcal{L}_\text{KL}$$

where $\mathcal{L}_\text{rec}$ is the cross-entropy reconstruction loss and $\mathcal{L}_\text{KL}$ is the KL divergence between the encoder's posterior and the standard normal prior $\mathcal{N}(0, I)$.

The reconstruction loss uses **leave-one-out (LOO)** encoding: when reconstructing pair $i$, the encoder sees all pairs *except* $(x_i, y_i)$. This prevents memorization and forces the encoder to generalize the program from the remaining pairs.

## 3. The Testbed: Pattern-2D (Simplified)

### 3.1 Task Structure

Each task consists of $n = 4$ input-output pairs generated by a single underlying program. Each pair has:

- **Input $x_i$**: a $4 \times 4$ grid. The grid is mostly black (color 0), with a single blue pixel (color 1) placed at some anchor position $(r_i, c_i)$.
- **Output $y_i$**: the same $4 \times 4$ grid, with a $2 \times 2$ color tile pasted starting at the anchor position $(r_i, c_i)$.

The **anchor position** $(r_i, c_i)$ varies across examples within a task — different examples have the blue pixel at different locations. The anchor is constrained so that the $2 \times 2$ tile fits within the $4 \times 4$ grid when pasted at that position.

The **color tile $T$** is a $2 \times 2$ matrix of colors drawn from the 10-color ARC palette. The tile is fixed for the entire task — it is the same across all 4 pairs. This is the program-invariant element.

**Summary:**
- Invariant (same across all pairs): the $2 \times 2$ tile $T$
- Variant (different across pairs): the anchor position $(r_i, c_i)$
- Colors: 10 possible values (ARC palette: 0=black, 1=blue, 2–9 other colors)
- Grid size: $4 \times 4$
- Tile size: $2 \times 2$ (4 cells total)
- Anchor color: fixed as blue (color 1) — hardcoded, not learned

The number of possible programs (unique tiles) is $10^4 = 10{,}000$. Tasks are sampled by drawing a tile $T$ and then drawing 4 anchor positions uniformly at random from valid positions.

### 3.2 Why This Testbed

The paper's Section B.4 explicitly uses this 4×4 / 2×2 setup to visualize how $z$ organizes around tile patterns, reducing the latent dimension to $d = 2$ for plotting. This makes it the natural proving ground for interpretability: the program is simple enough to verify completely, but rich enough to be non-trivial ($10{,}000$ possible programs).

## 4. Our Extension: The Interpretability Module

### 4.1 Core Idea

The original LPN decoder implicitly finds the anchor and reads the tile from $z$. We make this explicit by adding two components:

1. **An MLP head $h(z)$** that takes the latent $z$ as input and outputs a soft $2 \times 2$ color tile $\hat{S}$.
2. **A differentiable execution module** that combines $\hat{S}$ with the input $x_i$ to produce a predicted output grid.

These run *alongside* the original decoder — they do not replace it. At evaluation, the decoder's output is the prediction; the MLP head's output is the inspectable program readout.

### 4.2 The MLP Head $h(z)$

The MLP head takes only $z$ as input — it never sees $x_i$. This is a deliberate design constraint: because $z$ does not encode anchor position (variant, cancelled by mean pooling), the MLP can only succeed by learning to read the tile colors from $z$. This is exactly the information we want to make explicit.

Architecture:

$$z \in \mathbb{R}^d \;\to\; \text{Linear}(d, H) + \text{ReLU} \;\to\; \text{Linear}(H, H) + \text{ReLU} \;\to\; \text{Linear}(H, 4 \times 10)$$

The final layer produces $4 \times 10$ logits — one 10-way distribution per tile cell. A softmax is applied independently over each cell's 10 color logits to produce the **soft tile** $\hat{S} \in [0,1]^{4 \times 10}$:

$$\hat{S}_{c, k} = \frac{\exp(\text{logit}_{c,k})}{\sum_{k'} \exp(\text{logit}_{c,k'})}, \quad c \in \{0,1,2,3\},\; k \in \{0,\ldots,9\}$$

$\hat{S}_{c, \cdot}$ is a probability distribution over 10 colors for cell $c$. This is a **soft, differentiable** representation of the tile. At evaluation time only, the hard tile is recovered by argmax:

$$\hat{T}_c = \arg\max_k \hat{S}_{c,k}$$

During training, no argmax is taken — $\hat{S}$ remains soft throughout.

### 4.3 The Differentiable Execution Module

The execution module takes the soft tile $\hat{S}$ and an input grid $x_i$, and produces a predicted output grid $\hat{Y}_i$.

**Step 1 — FIND:** Locate the anchor position in $x_i$. The anchor is always the single blue pixel. This is a **deterministic, hardcoded lookup** — find the unique pixel with value 1 (blue) in the $4 \times 4$ grid. No learning involved. The output is an anchor position $(r_i, c_i)$.

This hardcoding is justified because: (a) we know by task construction that there is exactly one blue pixel per input, and (b) the original LPN decoder must also be finding the blue pixel to produce correct outputs — it does so via learned attention, but the operation is equivalent. We are making that implicit attention explicit.

**Step 2 — PASTE:** Scatter the soft tile $\hat{S}$ into the output grid at position $(r_i, c_i)$.

The output grid $\hat{Y}_i$ is initialized as a copy of $x_i$ (all black except the anchor). Then for each tile cell $c$ corresponding to grid offset $(\Delta r, \Delta c)$, the output distribution at grid position $(r_i + \Delta r, c_i + \Delta c)$ is set to $\hat{S}_{c, \cdot}$.

This operation is differentiable because $\hat{S}$ is a continuous probability vector — no hard decisions are made. The gradient flows through $\hat{S}$ back to the MLP head and then back to $z$.

**Boundary behavior:** Anchor positions are constrained at data generation time so the $2 \times 2$ tile always fits within the $4 \times 4$ grid. No boundary clipping is needed.

## 5. Two Architectures

We implement two versions, in order of complexity.

### Architecture 1: Tile Only (Baseline Interpretability)

The MLP head outputs the $2 \times 2$ tile. The offset from the anchor to the tile's top-left corner is **hardcoded to $(0, 0)$** — the tile is pasted exactly at the anchor position.

This is the simplest possible interpretable architecture. The program has one invariant component (the tile $T$), and the only latent program inference task for the MLP is to recover $T$ from $z$.

Execution: `FIND(x_i)` → anchor $(r, c)$ → `PASTE(S_hat, r, c)` → $\hat{Y}_i$

### Architecture 2: Tile + Offset (Compositional Interpretability)

The MLP head is split into two sub-heads sharing the same backbone:

- **Tile head:** same as Architecture 1, outputs $\hat{S} \in [0,1]^{4 \times 10}$
- **Offset head:** outputs a predicted offset $\hat{\delta} \in \mathbb{R}^2$ (or a discrete distribution over valid offsets)

The offset $\hat{\delta} = (\delta_r, \delta_c)$ shifts the paste position: the tile is pasted at $(r_i + \delta_r, c_i + \delta_c)$ rather than directly at the anchor. The offset is task-invariant (the same for all pairs in a task) but varies across tasks.

This architecture tests whether the MLP can simultaneously recover two invariant program components from $z$. The interpretability claim extends: $\text{argmax}(\hat{S})$ plus $\hat{\delta}$ together give the full human-readable program.

The offset is constrained so that the tile still lands within the grid for all valid anchor positions. Whether to represent offset as a continuous regression target or a discrete classification over a small set of valid offsets is a hyperparameter decision to explore.

## 6. The Modified Training Objective

Training proceeds on $z_0$ (the encoder output, with reparameterization). Three loss terms are computed:

### $\mathcal{L}_\text{dec}$ — Decoder Reconstruction Loss

The original LPN loss. Cross-entropy between the decoder's output distribution and the ground-truth output grid, summed over all $n$ pairs:

$$\mathcal{L}_\text{dec} = \sum_{i=1}^n \mathcal{L}_\text{CE}(\text{decoder}(x_i, z_0),\; y_i)$$

This is the primary training signal. It trains the encoder and decoder jointly to represent and use the program in $z$.

### $\mathcal{L}_\text{exec}$ — Execution Consistency Loss

Run the MLP head on $z_0$ to get $\hat{S}$, then run the execution module on each pair to get $\hat{Y}_i = \text{EXECUTE}(\hat{S}, x_i)$. Compare to ground truth:

$$\mathcal{L}_\text{exec} = \sum_{i=1}^n \mathcal{L}_\text{CE}(\hat{Y}_i,\; y_i)$$

This loss teaches the MLP head to produce a tile that, when actually executed, produces the correct output. It creates a training signal that flows from the execution result back through PASTE, through $\hat{S}$, through the MLP head, and into $z_0$.

Importantly, this loss also puts gentle pressure on the encoder to organize $z$ around the tile. If $z$ already encodes the tile well, the MLP head's job becomes easy, and $\mathcal{L}_\text{exec}$ becomes small.

### $\mathcal{L}_\text{commit}$ — Commitment Penalty

Penalize entropy in $\hat{S}$, encouraging the soft tile to become a peaked (committed) distribution over a single color per cell:

$$\mathcal{L}_\text{commit} = \sum_{c=0}^{3} H(\hat{S}_{c, \cdot}) = -\sum_{c=0}^{3} \sum_{k=0}^{9} \hat{S}_{c,k} \log \hat{S}_{c,k}$$

High entropy means the MLP is uncertain (fuzzy mixture of colors). Low entropy means it has committed to a specific color per cell — the result is interpretable. This loss pushes the soft tile toward crispness without requiring a hard argmax during training.

### Combined Loss

$$\mathcal{L}_\text{total} = \mathcal{L}_\text{dec} + \lambda_\text{exec} \cdot \mathcal{L}_\text{exec} + \lambda_\text{commit} \cdot \mathcal{L}_\text{commit} + \beta \cdot \mathcal{L}_\text{KL}$$

Starting hyperparameter values: $\lambda_\text{exec} = 1.0$, $\lambda_\text{commit} = 0.1$, $\beta = 10^{-4}$.

## 7. Training vs. Test-Time Pipelines

These differ in whether latent optimization is applied, and must be implemented as two distinct code paths.

### Training Pipeline

For each training batch (one task = one set of $n$ I/O pairs):

1. Encode the $n$ pairs with LOO: for each pair $i$, encode the other $n-1$ pairs to get $(\mu_{-i}, \sigma_{-i})$.
2. Sample $z_0^{(i)} = \mu_{-i} + \sigma_{-i} \odot \varepsilon$, $\varepsilon \sim \mathcal{N}(0, I)$.
3. Compute $\mathcal{L}_\text{dec}^{(i)}$: decoder cross-entropy on pair $i$ using $z_0^{(i)}$.
4. Compute $\mathcal{L}_\text{exec}^{(i)}$ and $\mathcal{L}_\text{commit}^{(i)}$ from the MLP head applied to $z_0^{(i)}$.
5. Sum losses over all $i$, add $\mathcal{L}_\text{KL}$, backpropagate through encoder, decoder, and MLP head jointly.

No latent optimization steps are performed during training (or at most 1–5 steps, treated as a hyperparameter).

### Test-Time Pipeline

Given a new test input $x_{n+1}$ and context pairs $\{(x_i, y_i)\}_{i=1}^n$:

1. Encode the $n$ context pairs (no LOO) to get $z_0 = \mu$.
2. Perform latent optimization: for $K$ steps, update $z$ by gradient ascent on $\mathcal{L}_\text{dec} + \lambda_\text{exec} \cdot \mathcal{L}_\text{exec} + \lambda_\text{commit} \cdot \mathcal{L}_\text{commit}$. All network weights are frozen; only $z$ changes.
3. Arrive at $z^*$.
4. **Decoder path (prediction):** $\hat{y}_{n+1} = \text{decoder}(x_{n+1}, z^*)$ — the actual output prediction.
5. **MLP head path (interpretability readout):** $\hat{T} = \text{argmax}(h(z^*))$ — the human-readable $2 \times 2$ color tile.

The decoder path is what is evaluated for reconstruction accuracy. The MLP head path is what is evaluated for tile recovery accuracy.

## 8. Evaluation

### Primary Metric: Tile Recovery Accuracy

Does the hard tile $\hat{T} = \text{argmax}(h(z^*))$ match the ground-truth tile $T$ used to generate the task?

Report both:
- **Cell-level accuracy**: fraction of the 4 cells that are correct.
- **Full-tile accuracy**: fraction of tasks where all 4 cells are correct.

This is the interpretability metric. A high score means the MLP head is reading the program from $z$ correctly.

### Secondary Metric: Reconstruction Accuracy

Does the decoder's output $\hat{y}_{n+1}$ match the ground-truth output $y_{n+1}$?

This verifies that adding the MLP head and its losses does not degrade the baseline LPN. If reconstruction accuracy drops significantly relative to a vanilla LPN run, the auxiliary losses are interfering with the core task and $\lambda$ values need tuning.

### Diagnostic Metrics

- **Tile entropy over optimization steps:** Plot $H(\hat{S}) = \sum_c H(\hat{S}_{c,\cdot})$ as a function of latent optimization step $k$. Entropy should decrease as $z$ moves from $z_0$ toward $z^*$ — the tile commitment should sharpen during optimization.
- **Decoder–executor agreement:** At test time, compare the decoder's output to the executor's output (the grid produced by PASTE). If both are correct and agree, the two paths are consistent. If the decoder is correct but the executor is not, $z$ is usable but the MLP is failing to read it correctly.
- **Latent trajectory visualization:** For the 4×4 / 2×2 testbed with $d = 2$, plot $z_0, z_1, \ldots, z^*$ for several tasks to show that gradient ascent moves $z$ toward the correct region of latent space.

## 10. Key Design Principles to Preserve in Implementation

**The MLP head never sees $x$.** It receives only $z$ as input. Any accidental leakage of $x$ into the MLP (e.g., through the executor's gradient) should be understood but not blocked — the gradient of $\mathcal{L}_\text{exec}$ flows through PASTE and back into $\hat{S}$ and $z$, which is intentional. But the MLP's forward pass takes only $z$.

**The decoder is not replaced.** The decoder and MLP head are parallel readouts of $z^*$. The decoder produces the prediction; the MLP head produces the explanation. Both are trained jointly; both contribute to the loss.

**Soft tile throughout training.** No argmax during training — all operations on $\hat{S}$ must be differentiable. Argmax is used only at evaluation time to produce $\hat{T}$.

**LOO is applied correctly.** When computing the loss for pair $i$, the latent $z_0^{(i)}$ must be computed from all pairs *except* pair $i$. This is non-trivial to batch efficiently and is worth implementing carefully.

**Latent optimization is a distinct code path.** At test time, the optimizer acts on $z$ (a tensor that requires gradient) while keeping all model parameters frozen. This is different from training, where parameters are updated and $z$ is recomputed from the encoder each forward pass. These two modes must be clearly separated in the implementation.

**Boundary conditions.** The dataset generator must ensure that all sampled anchor positions allow the full $2 \times 2$ tile to be pasted within the $4 \times 4$ grid. Valid anchor positions are rows $\{0, 1, 2\}$ and columns $\{0, 1, 2\}$, giving 9 possible anchor positions. The anchor must not coincide with any tile cell that would be a non-black color — i.e., the blue anchor pixel at $(r, c)$ is overwritten by the tile during PASTE, which is expected behavior.

## 11. What Success Looks Like

The project succeeds if we can show:

1. The MLP head recovers the ground-truth tile with high cell-level accuracy (>90%) and reasonable full-tile accuracy after latent optimization.
2. Reconstruction accuracy with the interpretability module is not significantly below vanilla LPN (within a few percentage points).
3. The entropy of $\hat{S}$ decreases monotonically during latent optimization — showing that the optimization is committing to a specific program reading.
4. For Architecture 2, both the tile *and* the offset are recovered correctly, demonstrating that multiple invariant program components can be simultaneously packed into and read from $z$.

The deeper conceptual success: at the end of a run, a human can inspect $\hat{T}$ and verify by eye that it matches the ground-truth tile used to generate the task. This is interpretability — not a number, but a legible program.
